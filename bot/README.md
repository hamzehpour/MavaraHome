# پلتفرم رزرو و مدیریت رویداد خانه ماورا

ربات تلگرام رزرو بلیت + پنل مدیریت کامل داخل تلگرام، با معماری ماژولار
(handlers / services / repositories) که برای رشد به سمت وب‌سایت، اپلیکیشن،
درگاه پرداخت و API عمومی طراحی شده — بدون نیاز به بازنویسی، فقط با افزودن
لایه‌های جدید کنار همین core.

## راه‌اندازی

```bash
python3 -m venv venv
source venv/bin/activate          # ویندوز: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# .env را باز کن و BOT_TOKEN و BOOTSTRAP_ADMIN_IDS را پر کن
```

`BOOTSTRAP_ADMIN_IDS` فقط برای اولین اجرا استفاده می‌شود (اولین ادمین را
می‌سازد). بعد از آن، مدیریت ادمین‌ها از خود ربات با ورود مستقیم به جدول
`admins` یا با افزودن یک هندلر `/addadmin` در آینده انجام می‌شود.

```bash
python bot.py
```

اولین اجرا به‌صورت خودکار دیتابیس (`data/mavara.db`) و تنظیمات پیش‌فرض را
می‌سازد. سپس از پنل مدیریت (`/admin` داخل تلگرام) نام مجموعه، قیمت بلیت،
شماره کارت، متن خوش‌آمدگویی و قوانین را وارد کن.

## ساختار پروژه

```
bot.py                  نقطه ورود، فقط سیم‌کشی روترها
config/settings.py       فقط مقادیر امنیتی/محیطی (از .env)
database/                اتصال، schema، و repository ها (لایه دیتابیس)
services/                منطق کسب‌وکار (رزرو، پرداخت، تنظیمات، آمار، ...)
handlers/                هندلرهای تلگرام (نازک — فقط UI + صدا زدن service)
keyboards/                کیبوردهای اینلاین/ریپلای
states/                   وضعیت‌های FSM
texts/fa.py               تمام متن‌های فارسی — تنها جایی که باید ویرایش شود
validators/                اعتبارسنجی ورودی، بدون وابستگی به تلگرام
utils/                     کد رزرو، QR، لاگر
filters/, middlewares/     دسترسی ادمین، لاگ خودکار هر پیام + بلاک کاربر
logs/                      فایل لاگ چرخشی (app.log)
```

## مستندات فنی کامل

### نمودار جدول‌های دیتابیس (ER — به‌صورت متنی)

```
users (id, telegram_id*, full_name, phone, is_blocked, created_at)
  │
  ├──< reservations (id, reservation_code*, user_id→users, session_id→sessions,
  │        people, unit_price, total_price, status, source, created_by_staff,
  │        attendee_name, attendee_phone, admin_note, created_at, updated_at, expires_at)
  │        │
  │        └──< payments (id, reservation_id→reservations, receipt_file_id,
  │                 receipt_source, amount, status, submitted_at, reviewed_at, reviewed_by)
  │
  └──< waiting_list (id, user_id→users, session_id→sessions, people, status, created_at)

events (id, title, description, address, icon, is_active, created_at)
  └──< sessions (id, event_id→events, session_date, session_time, capacity, status, created_at)

```

### تمام وضعیت‌های رزرو (State Machine)

```
pending_payment            → مشتری هنوز رسید نفرستاده (مهلت‌دار — منقضی می‌شود)
      │
      ▼ (رسید ارسال شد)
pending_review              → منتظر تصمیم ادمین
      │
      ├──▶ approved                     (تأیید نهایی — بلیت/QR صادر می‌شود)
      │
      └──▶ awaiting_buyer_confirmation  → (رد اولیه — صندلی هنوز نگه داشته می‌شود)
                 │
                 ├──▶ rejected (خریدار پذیرفت، یا ادمین در بحث نهایی رد کرد)
                 └──▶ approved (ادمین در بحث نهایی پذیرفت)

waiting     → مشتری در لیست انتظار (سانس پر بوده)
expired     → خودکار، اگر رسید تا مهلت تعیین‌شده نرسد
cancelled   → لغو دستی توسط ادمین
used        → بلیت در ورودی اسکن و تأیید شده
```

هر انتقال حساس (approve / reject / accept-cancel) با `set_status_if` به‌صورت اتمیک انجام می‌شود —
یعنی اگر همان دکمه دوبار زده شود یا دو ادمین همزمان تصمیم بگیرند، فقط اولین تلاش واقعاً اثر می‌کند.

### Flow رزرو (مشتری)

```
انتخاب رویداد → انتخاب روز (تقویم شمسی، روزهای گذشته غیرفعال)
→ انتخاب سانس → تعداد (➕➖) → برای خودم/شخص دیگری
→ (اگر برای دیگری: نام+شماره فرد حاضر) → نام/شماره خریدار (یا استفاده از قبلی)
→ مرور نهایی → ثبت رزرو (pending_payment) → نمایش شماره کارت
```

### Flow پرداخت

```
مشتری عکس رسید می‌فرستد → pending_review → همه مسئولان مطلع می‌شوند
  → ادمین تأیید می‌زند → approved → کد+QR امضاشده برای مشتری ارسال می‌شود
  → ادمین رد می‌زند → awaiting_buyer_confirmation (صندلی هنوز نگه داشته می‌شود)
      → خریدار می‌پذیرد → rejected (صندلی آزاد می‌شود)
      → خریدار اعتراض می‌کند → به همه مسئولان می‌رود → تصمیم نهایی (approved یا rejected)
```

### Flow ظرفیت

```
هر سانس یک capacity ثابت دارد.
"پر شدن" = مجموع people در وضعیت‌های
  pending_payment + pending_review + awaiting_buyer_confirmation + approved
  (یعنی حتی رزرو تأییدنشده هم تا زمانی که رد/منقضی نشده، جای خودش را نگه می‌دارد)

اگر ظرفیت کافی نبود → مشتری در waiting_list ثبت می‌شود و به مسئولان اطلاع داده می‌شود
  → اگر ادمین تأیید کند: ظرفیت سانس و ثبت رزرو در یک تراکنش اتمیک انجام می‌شود
    (این‌طوری دو نفر نمی‌توانند همان ظرفیت تازه‌باز‌شده را همزمان بردارند)
```

### بک‌آپ و ریستور

**بک‌آپ خودکار:** هر ۲۴ ساعت یک‌بار، کل فایل دیتابیس در پوشه `backups/` با نام
`mavara_backup_<تاریخ‌وساعت>.db` کپی می‌شود؛ فقط ۱۴ نسخه آخر نگه داشته می‌شود.

**ریستور (دستی — عمداً خودکار نشده، چون overwrite کردن دیتابیس زنده خطرناک است):**
```bash
# ربات را متوقف کن
sudo systemctl stop mavara-bot   # یا هر روشی که اجرا می‌کنی

# دیتابیس فعلی را با نسخه بک‌آپ جایگزین کن
cp backups/mavara_backup_<تاریخ‌ای‌که‌میخوای>.db data/mavara.db

# ربات را دوباره روشن کن
sudo systemctl start mavara-bot
```

### متغیرهای `.env`

| متغیر | توضیح |
|---|---|
| `BOT_TOKEN` | توکن ربات از BotFather — هرگز کامیت نشود |
| `BOOTSTRAP_ADMIN_IDS` | آیدی عددی اولین مالک (فقط برای اولین اجرا) |
| `DB_PATH` | مسیر فایل دیتابیس (پیش‌فرض `data/mavara.db`) |
| `LOG_FILE` | مسیر فایل لاگ (پیش‌فرض `logs/app.log`) |

سایر تنظیمات (قیمت، ظرفیت، متن‌ها، شماره کارت، رمز مالکیت، …) همه از دیتابیس/پنل ادمین می‌آیند،
نه از `.env` — این عمداً است تا تغییرشان نیاز به دیپلوی مجدد نداشته باشد.

### وضعیت آماده‌بودن برای API/سایت آینده

هندلرهای تلگرام (`handlers/`) هیچ منطق کسب‌وکاری ندارند — فقط `services/` را صدا می‌زنند.
`services/` و `database/` هیچ وابستگی‌ای به aiogram ندارند (تأیید شده با اسکن خودکار). یعنی وقتی
سایت ساخته شد، یک لایه API (مثلاً FastAPI) می‌تواند مستقیم همین توابع `services/` را صدا بزند —
بدون بازنویسی منطق رزرو، ظرفیت، پرداخت یا انقضا.



- **هیچ رمز/توکنی داخل کد نیست** — همه از `.env` می‌آیند و `.env` در
  `.gitignore` است.
- **شماره کارت و قیمت از دیتابیس خوانده می‌شوند**، نه از کد — از پنل
  مدیریت قابل تغییرند.
- فایل دیتابیس (`data/*.db`) و لاگ‌ها (`logs/*.log`) هم gitignore شده‌اند؛
  این‌ها داده کاربران واقعی هستند و هرگز نباید کامیت شوند.
- تمام کوئری‌های دیتابیس Parameterized هستند (بدون خطر SQL Injection).
- بررسی ظرفیت و ثبت رزرو داخل یک تراکنش واحد انجام می‌شود تا رزرو
  هم‌زمانِ دو کاربر باعث فروش بیش از ظرفیت نشود.

### پاک‌سازی مخزن قدیمی گیت‌هاب (ضروری)

مخزن قبلی (`mavara-bot`) شامل توکن ربات، شماره کارت، و یک فایل دیتابیس
با اطلاعات واقعی کاربران در تاریخچه کامیت‌هاست. صرفاً حذف کردن فایل‌ها در
یک کامیت جدید کافی نیست چون در تاریخچه باقی می‌مانند. پیشنهاد:

1. مخزن گیت‌هاب را روی **Private** بگذار (اگر پابلیک است) — همین الان.
2. مطمئن شو توکن قدیمی در BotFather ریووک شده (طبق گفته شما، انجام شده ✅).
3. این پروژه جدید را به‌عنوان یک **مخزن تازه** (بدون تاریخچه آلوده) push کن؛
   ساده‌ترین و مطمئن‌ترین راه، به‌جای پاک‌سازی تاریخچه قدیمی.

```bash
cd mavara-bot-v2
git init
git add .
git commit -m "Initial commit: modular event management platform"
git remote add origin <آدرس مخزن جدید یا همان مخزن قدیمی بعد از پاک کردن>
git push -u origin main --force   # فقط اگر مخزن قدیمی را کامل جایگزین می‌کنی
```

## نسخه ۸ — سخت‌سازی هسته سیستم + کانال مانیتورینگ زنده

✅ **رفع Race Condition واقعی**: ویرایش دستی تعداد نفرات و جابجایی رزرو، چک ظرفیت و نوشتن را

درست تشخیص داده بود)
✅ **تکمیل محافظت Idempotency**: چند نقطه (رد پرداخت، پذیرش کنسلی توسط خریدار، رد اضافه‌ظرفیت)
حالا هم مثل تأیید پرداخت، با تراکنش اتمیک محافظت می‌شوند — دیگر دابل‌تپ روی دکمه‌ها اثر دوباره ندارد
✅ **README کامل**: نمودار ER، همه وضعیت‌های رزرو، Flow رزرو/پرداخت/ظرفیت، بک‌آپ/ریستور، دیپلوی، متغیرهای env
✅ **کانال مانیتورینگ فروش زنده**: از پنل → «📡 راه‌اندازی کانال مانیتورینگ» → یک پیام از آن کانال
فوروارد کنید (ربات باید در آن کانال ادمین با دسترسی ارسال پیام باشد). از آن به بعد، برای هر روزی
که سانس دارد، یک پیام زنده در کانال ساخته و با هر تغییر (رزرو جدید، تأیید/رد نهایی، لغو، جابجایی،
تغییر تعداد/ظرفیت، انقضا) خودکار ویرایش می‌شود — دقیقاً همان قالبی که فرستادید (تاریخ شمسی بالای هر
روز، هر سانس شماره‌گذاری‌شده با آیکن ساعت و دایره وضعیت 🟢/🟠، لیست افراد با تعداد و شماره).
اگر محتوای یک روز از حد مجاز تلگرام بیشتر شود، به چند پیام تقسیم می‌شود و هر پیام بعدی عنوان
«ادامه» همان روز/سانس را دارد تا گم نشوید. بین روزها یک بنر جداکننده (⛵️⛵️⛵️...) و بین هفته‌ها
یک بنر متفاوت (🆕🆕🆕...) فرستاده می‌شود. **توصیه: خودتان دستی چیزی در آن کانال ویرایش نکنید** —
چون ربات آن پیام‌ها را مالک است و اگر شما هم دستی تغییر بدهید، با آپدیت بعدی ربات بازنویسی می‌شود.

✅ **پیام به یک نفر مشخص**: از پنل، «✉️ پیام به یک نفر» — با یوزرنیم یا آیدی عددی

## نسخه ۶ — ۵ اولویت بعدی (خودم به ترتیب اولویت انتخاب و انجام دادم)

✅ **صندلی تا تعیین‌تکلیف نهایی آزاد نمی‌شود**: رد پرداخت حالا دومرحله‌ای است — وقتی ادمین رد
می‌زند، صندلی هنوز نگه داشته می‌شود؛ برای خریدار پیام می‌رود که «می‌پذیرم، کنسل شود» یا
«توضیح می‌دهم». اگر اعتراض کند، توضیحش برای همه مسئولان می‌رود تا تصمیم نهایی (تأیید یا رد
قطعی) گرفته شود. فقط با تصمیم نهایی، صندلی آزاد می‌شود.
✅ **دو زمان انتظار جدا در تنظیمات**: مهلت ارسال رسید توسط خریدار (پیش‌فرض ۱۵ دقیقه، همچنان
خودکار منقضی می‌شود) و یادآوری به ادمین اگر بررسی دیرتر از حد معین طول کشید (پیش‌فرض ۱ ساعت —
این یکی هرگز صندلی را آزاد نمی‌کند، فقط دوباره به ادمین/مسئولان یادآوری می‌کند)
✅ **مدیریت دستی رزروهای ثبت‌شده**: از صفحه هر سانس → «مدیریت رزروهای ثبت‌شده» → برای هر
رزرو می‌توانید تعداد نفرات را عوض کنید، به سانس دیگری جابجا کنید، یا لغو کنید
✅ **آدرس/شناسنامه رویداد**: هر رویداد آدرس مخصوص به خودش دارد و خودکار در متن نهایی بلیت

✅ **حذف دکمه‌های اضافه بعد از تصمیم رزرو**: دکمه‌های ویرایش نام/شماره/انصراف مرحله مرور،
بلافاصله بعد از ادامه به پرداخت از پیام پاک می‌شوند

## نسخه ۵ — بر اساس تست کامل شما در ۹ مرداد

با بررسی لاگ واقعی شما تأیید شد: کل جریان رزرو، تأیید/رد، کارت‌های بانکی، و ویرایش ظرفیت
بدون هیچ خطایی کار می‌کنند — یعنی رفع باگ QR در نسخه قبل واقعاً جواب داد. ✅

این نسخه شامل:

✅ **پیام همگانی حالا به تفکیک است** (این را در پیام قبلی‌تان هم خواسته بودید و حق با شماست که
جا افتاد — این بار انجام شد): همه کاربران / کسانی که دیده‌اند / کسانی که هنوز ندیده‌اند / یک
روز یا سانس مشخص
✅ رفع باگ شماره موبایل فارسی: با بررسی لاگ دقیقاً دیدم که وقتی با اعداد فارسی شماره را
می‌فرستادید رد می‌شد (چون کاراکتر فارسی ۰۹ در کد با ASCII "09" یکی نیست) — رفع شد، هم عدد
فارسی هم انگلیسی حالا قبول و در دیتابیس یکدست (انگلیسی) ذخیره می‌شود
✅ در تقویم انتخاب سانس، روزهای گذشته حالا غیرفعال‌اند (کلیک نمی‌شوند) ولی دیده می‌شوند

### درباره «رزروهای در انتظار بررسی که هیچی نشون نمیده»

از لاگ شما بررسی کردم — نگران‌کننده نیست: در همان لحظه که این دکمه را زدید، همه رزروهای
موجود از قبل تأیید یا رد شده بودند (صفر مورد در انتظار واقعی وجود داشت). ربات باید پیام
«در حال حاضر رزرو در انتظار بررسی وجود ندارد» را نشان بدهد — اگر آن پیام را ندیدید و صفحه
واقعاً کاملاً خالی ماند، لطفاً دفعه بعد دقیقاً بگویید چه چیزی (یا هیچ‌چیز) دیدید تا دقیق‌تر پیگیری کنم.

### فهرست باقی‌مانده (این لیست دارد بزرگ می‌شود — پیشنهاد می‌کنم دفعه بعد بگویید کدام‌ها برایتان
### فوری‌ترند تا آن‌ها را زودتر از بقیه انجام بدهم)

- منطق «ظرفیت پر شد، درخواست اضافه‌ظرفیت از ادمین» + تأیید دوطرفه لغو رزرو با کاربر
- تا زمان تعیین‌تکلیف نهایی (نه فقط رد اولیه)، صندلی آزاد نشود
- دو زمان انتظار جدا (پرداخت / تأیید مدیر) در تنظیمات
- مدیریت سانس: جابه‌جایی/ویرایش دستی رزروهای ثبت‌شده توسط ادمین
- کانال مانیتورینگ فروش زنده با قالب قابل‌ویرایش
- آمار فروش با بازه تاریخی و تفکیک روز/سانس + دکمه دیدن لیست شماره‌ها
- شناسنامه رویداد (آدرس/لوکیشن) در تنظیمات مدیریت رویدادها
- افزودن مسئول با یوزرنیم به‌جای آیدی عددی + انتقال مالکیت ربات
- زیباتر کردن صفحه مدیریت کارت‌های بانکی (آیکن بانک‌ها)
- پاک‌شدن کیبورد دستوری برای مشتری بعد از خرید نهایی
- انتخاب آیکن رویداد توسط ادمین هنگام ساخت
- تعداد سانس هنگام ساخت هم با دکمه ➕➖ (الان فقط ساعت/دقیقه سانس‌های تکی این‌طور نیستند، تعداد را تایپ می‌کنید)
- ارسال پیام به یک کاربر مشخص (نه کل گروه)
- لاگ کامل تغییرات/حذف‌ها به‌صورت اکسل قابل‌پیگیری

## نسخه ۴ — رفع باگ اصلی + امکانات جدید (بر اساس لاگ واقعی شما)

🎯 **رفع ریشه‌ای باگ «تأیید کردم ولی چیزی نیومد»**: با بررسی فایل لاگ واقعی شما، دلیل دقیق پیدا شد —
تابع ساخت QR یک نوع داده نادرست به تلگرام می‌داد که باعث خطای اعتبارسنجی و شکست کامل ارسال عکس بلیت
می‌شد. این باگ از همان نسخه اول وجود داشت. حالا کاملاً رفع شده و امتحان‌شده (از نظر منطق کد).

✅ کلیک روی شماره کارت برای کپی، حالا مستقل از نحوه ویرایش متن توسط ادمین همیشه کار می‌کند
✅ امکان ثبت تا ۱۰ کارت بانکی، انتخاب دستی کارت فعال، نمایش نام بانک، و چرخش خودکار هفتگی (اختیاری)
✅ رزرو برای شخص دیگر: می‌توانید مشخص کنید بلیت برای خودتان است یا کس دیگری؛ اگر برای دیگری باشد
نام و شماره آن فرد جدا ثبت می‌شود (حساب کاربری خودتان تغییر نمی‌کند) و در پنل ادمین/اکسل هم مشخص است
خریدار کیست و حاضر واقعی کیست
✅ لیست «رزروهای من» حالا سه بخش جدا دارد: در انتظار، بلیت‌های فعال، اجراهای دیده‌شده
✅ خروجی اکسل مرتب‌تر: ستون‌بندی درست، رنگ سرستون، تاریخ سانس به شمسی، ستون‌های خریدار/حاضر جدا

### هنوز باقی‌مانده (فهرست تجمیعی، برای مرحله بعد)

- منطق «ظرفیت نزدیک تکمیل / در صف تأیید» با پیام روان‌شناسانه‌تر + امکان اجازه اضافه‌ظرفیت توسط ادمین
- گزارش زنده در کانال تلگرام
- پیام همگانی به تفکیک سانس/روز خاص
- بازخورد صوتی تماشاگران (/feedbacks) و پوستر/تیزر (/sharing)
- آمار فروش تفکیکی (روز/سانس) به‌جای فقط جمع کل
- چک‌لیست راهنما برای اولین ورود ادمین
- تعیین دقیق دسترسی‌های هر مسئول توسط ادمین (تیک‌محور)
- متن پشتیبانی هم از پنل قابل‌ویرایش شود
- انتخاب ساعت سانس با گزینه‌های آماده به‌جای تایپ دستی

## نسخه ۳ — اصلاحات این مرحله (بر اساس تست واقعی شما)

✅ تقویم شمسی برای انتخاب تاریخ سانس (بدون هیچ کتابخانه بیرونی — پیاده‌سازی خالص پایتون در `utils/jalali.py`)
✅ افزودن چند سانس در یک روز بدون تکرار وارد کردن تاریخ (روز → تعداد سانس → ظرفیت → ساعت هرکدام)
✅ جلوگیری از ثبت سانس تکراری (هم در حین ورود، هم با قید یکتا در دیتابیس)
✅ حذف/غیرفعال‌سازی همیشه با یک پیام تأیید («بله، مطمئنم» / «انصراف») — دیگر با یک تپ اشتباه چیزی پاک نمی‌شود
✅ مدیریت اجراها: هر سانس ردیف جداگانه با دکمه‌های ✏️ ویرایش / 🟢🟠 فعال‌سازی / 🗑 حذف مخصوص به خودش
✅ نمایش وضعیت هر سانس (چند نفر رزرو کرده‌اند + نام و شماره تماس‌شان) از همان صفحه ویرایش سانس
✅ ترتیب نمایش سانس‌ها همیشه از تاریخ نزدیک‌تر به دورتر
✅ رزرو مشتری: نام رویداد همیشه نمایش داده می‌شود (حتی با یک رویداد فعال)، دکمه بازگشت در تمام مراحل، انتخاب تعداد با ➖ ➕ به‌جای صفحه اعداد
✅ اگر مشتری قبلاً رزرو داشته، نام/شماره‌اش پیشنهاد می‌شود («همینه» یا «ویرایش می‌کنم») — دیگر لازم نیست هر بار از نو تایپ کند
✅ مبلغ قابل‌پرداخت (تعداد × قیمت) — بررسی شد و در دیتابیس درست محاسبه می‌شود؛ اگر جایی نادرست دیدید دوباره خبر بدهید تا دقیق پیگیری کنم
✅ متن‌های «راهنمای پرداخت»، «رسید دریافت شد»، «بلیت نهایی بعد از تأیید»، و «رد پرداخت» همگی از پنل تنظیمات قابل‌ویرایش‌اند (با متغیرهایی مثل نام رویداد/تاریخ/تعداد/شماره کارت که خودشان جایگزین می‌شوند)
✅ رفع باگ «تأیید کردم ولی چیزی برای خریدار نیامد»: حالا اگر ارسال پیام به خریدار به هر دلیلی (بلاک کردن ربات و…) ناموفق باشد، به‌جای سکوت، به ادمین همان لحظه اطلاع داده می‌شود
✅ ادمین می‌تواند بعد از تأیید یک یادداشت کوتاه اختیاری هم برای خریدار بفرستد
✅ دکمه پشتیبانی حالا واقعاً کار می‌کند: شماره تماس (قابل‌تنظیم در پنل) + گزینه نوشتن پیام که مستقیم برای تیم فرستاده می‌شود و پاسخ هم به همان کاربر برمی‌گردد
✅ منوی متفاوت برای ادمین/مالک و مسئول پشتیبانی هنگام /start — دیگر لازم نیست دستور /admin را بزنید

### هنوز باقی‌مانده (برای مرحله بعد)

- گزارش زنده در کانال تلگرام (به‌روزرسانی خودکار وضعیت سانس‌ها)
- لیست مخاطبین با شماره قابل‌تماس (دسته‌بندی‌شده بر اساس سانس)
- زیرمنوی مخاطبان پیام همگانی (دیده‌اند/ندیده‌اند/سانس خاص) + امکان حذف بعد از ارسال
- محاسبه دستمزد حامی مالی هر سانس (درصد قابل‌تنظیم)
- کتابخانه پوستر/تیزر/نظرات تماشاگران برای هر رویداد
- زیباسازی بیشتر خروجی اکسل (ستون‌بندی، رنگ، تاریخ شمسی به‌حروف)
- درخواست مستقیم سانس توسط مشتری برای روزی که هنوز تعریف نشده (پیشنهاد شما — نیاز به بررسی بیشتر از نظر باگ‌خیز نبودن دارد)

## وضعیت فعلی (چه چیزی پیاده شده)

✅ رزرو کامل (تاریخ → سانس → تعداد → نام → تلفن → مرور/ویرایش → پرداخت → رسید)
✅ ظرفیت واقعی و جداگانه برای هر سانس + بدون race condition
✅ لیست انتظار خودکار وقتی سانس پر است
✅ پنل ادمین: تأیید/رد رزرو، مدیریت اجراها و سانس‌ها، آمار فروش،
   پیام همگانی، خروجی اکسل، تنظیمات پویا
✅ صدور کد رزرو یکتا + QR Code بعد از تأیید پرداخت
✅ وضعیت‌های کامل رزرو (pending_payment / pending_review / approved /
   rejected / waiting)
✅ لاگ‌گیری همه اکشن‌های مهم (فایل + دیتابیس)
✅ مسدودسازی کاربر (`is_blocked`) به‌صورت خودکار در میدلور
✅ **چند رویداد هم‌زمان**: هر رویداد جدید که در پنل ادمین ساخته و فعال شود،
   بلافاصله در ربات برای رزرو در دسترس است. اگر فقط یک رویداد فعال باشد،
   ربات همان را مستقیم نشان می‌دهد (بدون مرحله اضافه)؛ با بیش از یک رویداد
   فعال، کاربر ابتدا رویداد را انتخاب می‌کند.
✅ **دو سطح دسترسی پنل مدیریت**:
   - **ادمین/مالک**: دسترسی کامل به همه بخش‌ها (تنظیمات، مدیریت اجراها،
     پیام همگانی، خروجی اکسل، مدیریت مسئولان).
   - **مسئول پشتیبانی/رزرو تلفنی** (نقش `operator`): فقط می‌تواند رزروهای
     در انتظار را تأیید/رد کند، ظرفیت سانس‌ها را ببیند، و برای تماس تلفنی
     یک رزرو دستی ثبت کند (بدون دسترسی به تنظیمات یا مدیریت اجراها).
     افزودن/حذف این افراد فقط از طریق ادمین/مالک و از داخل پنل
     («👥 مدیریت مسئولان») با وارد کردن آیدی عددی تلگرام آن‌ها انجام می‌شود.
✅ **رزرو تلفنی توسط مسئول پشتیبانی**: در همان لحظه رزرو ثبت و بلیت صادر
   می‌شود (نیازی به ارسال رسید نیست چون پرداخت توسط خود مسئول تأیید شده)،
   و مسئول می‌تواند کد رزرو را تلفنی به مشتری اعلام کند. برای مشتریانی که
   حساب تلگرام ندارند هم کار می‌کند (رزرو بر اساس شماره تلفن ثبت می‌شود).
✅ **انقضای خودکار رزروهای پرداخت‌نشده**: اگر کاربر ظرف مدت مشخص‌شده در
   تنظیمات (`payment_expiry_minutes`، پیش‌فرض ۶۰ دقیقه) رسید ارسال نکند،
   رزرو به‌صورت خودکار منقضی و ظرفیت آزاد می‌شود؛ یک وظیفه پس‌زمینه هر
   ۲ دقیقه این را بررسی می‌کند.

## نسخه ۱۱.۱ — رفع باگ‌های بحرانی گزارش‌شده در تست واقعی

### 🔴 باگ اصلی (بلاک‌کننده تست): "ادامه پرداخت" چیزی نمی‌فرستد + TelegramBadRequest
**Root cause واقعی:** پیام «راهنمای پرداخت» از یک Template قابل‌ویرایش ادمین (شماره
کارت، نام صاحب کارت) ساخته و با `parse_mode="Markdown"` ارسال می‌شد. یک `_` یا `*`
نامتوازن در نام صاحب کارت یا متن Template کافی بود که Telegram کل پیام را رد کند
(`can't parse entities`) — و چون این ارسال بدون هیچ fallback ای بود، کاربر عملاً
هیچ پیامی نمی‌دید و در `awaiting_receipt` گیر می‌کرد.

**رفع:** یک ماژول مشترک `utils/safe_send.py` ساخته شد که هر ارسال را اول با
Markdown امتحان می‌کند و اگر Telegram دقیقاً به‌خاطر Markdown رد کرد، همان متن را
بدون فرمت دوباره می‌فرستد — پیام هرگز گم نمی‌شود. این روی **۶ نقطه** در کد که همین
الگو را داشتند اعمال شد (نه فقط همان یکی که گزارش شده بود): `booking.py` (خود باگ
گزارش‌شده)، `admin_reservations.py` (از قبل محافظت داشت)، `overflow_requests.py`،
`reject_confirmation.py`، `staff_manual_booking.py`، `admin_panel.py`.

### 🔴 باگ دوم: درخواست اضافه‌ظرفیت پیام «رسید بفرستید» نمی‌دهد و رسید را تشخیص نمی‌دهد
**Root cause:** وقتی ادمین یک درخواست اضافه‌ظرفیت را تأیید می‌کرد، پیام راهنمای
پرداخت برای خریدار ارسال می‌شد ولی: (۱) پیام «رسید ارسال کنید» اصلاً وجود نداشت،
(۲) FSM آن خریدار هرگز وارد `awaiting_receipt` نمی‌شد — چون آن هندلر رسید فقط روی
FSM state کاربرانی کار می‌کند که از مسیر عادی رزرو آمده باشند. نتیجه: خریدار رسیدش
را می‌فرستاد، ولی هیچ هندلری آن را نمی‌دید.

**رفع:** با دسترسی مستقیم به `dispatcher.storage`، FSM همان خریدار به‌صورت مستقیم
(نه از طریق callback خودش، چون این یک اکشن ادمین روی چت شخص دیگری است) وارد
`awaiting_receipt` با `reservation_id` درست می‌شود — دقیقاً همان مسیری که رزرو عادی
طی می‌کند، از همان‌جا تا صدور بلیت.
