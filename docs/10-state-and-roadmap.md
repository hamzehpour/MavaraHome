## ⚠️ نیمه‌کاره — بک‌اند هست، رابط کاربری نیست

### صندوق پیام‌های پشتیبانی

**تنها شکاف واقعی محصول.** جدول `messages`، ریپازیتوری، و چهار اندپوینت
API همه ساخته و سالم‌اند. مشتری هم می‌تواند از ربات پیام بفرستد. ولی:

- **هیچ صفحه‌ی `admin/messages.html` وجود ندارد** و هیچ‌جای پنل این
  اندپوینت‌ها را صدا نمی‌زند.
- یعنی پیام‌های پشتیبانی در دیتابیس می‌نشینند و ادمین از پنل نمی‌بیندشان.

**کار لازم:** یک صفحه‌ی پنل مثل بقیه (فهرست رشته‌ها ← نمایش گفت‌وگو ← پاسخ).
تخمین: کم — چون بک‌اندش آماده است.

## 🔍 بدهی فنی شناخته‌شده

به ترتیب اهمیت:

### ۱. لایه‌ی HTTP و ربات تست خودکار ندارند
۶۲ تست فقط لایه‌ی منطق را پوشش می‌دهند. **۶۷ مسیر API و ۱۷۵ هندلر تلگرام
هیچ تست خودکاری ندارند.** دقیقاً به همین دلیل بود که نبودِ مسیر حذف رویداد
هفته‌ها کشف نشد.

*پیشنهاد:* یک لایه‌ی تست HTTP که سرور را روی دیتابیس یک‌بارمصرف بالا بیاورد
و مسیرهای اصلی را بزند. الگویش در `09-troubleshooting` هست، فقط باید به
`test_bot.py` منتقل شود.

### ۲. دو نمایش متفاوت از «بلیت استفاده شد»
مسیر پذیرش در ربات وضعیت را `used` می‌کند؛ مسیر وب به‌جایش `checked_in_at`
را پر می‌کند و وضعیت را دست نمی‌زند. هر دو کار می‌کنند ولی یک مفهوم را دو
جور ثبت می‌کنند. باید یکی شوند — ترجیحاً روی `checked_in_at`، چون وضعیت
`approved` بعد از ورود هم معنادار است.

### ۳. مقیاس فاصله‌گذاری در CSS وجود ندارد
۲۴ توکن طراحی داریم و واقعاً استفاده می‌شوند، ولی هیچ `--space-*` نداریم و
فاصله‌ها اغلب inline هاردکد شده‌اند. تنها شکاف واقعی سیستم طراحی.

### ۴. وضعیت بازنشسته‌ی `awaiting_buyer_confirmation`
هیچ کدی دیگر نمی‌نویسدش ولی هنوز در شش جا خوانده می‌شود. بی‌خطر است (ردیف‌های
قدیمی صندلی‌شان را نگه می‌دارند) ولی برای تازه‌وارد گیج‌کننده است. وقتی مطمئن
شدی هیچ ردیفی با این وضعیت باقی نمانده، می‌شود حذفش کرد.

### ۵. `actor-portfolio/` — سایت متروک
یک فرانت‌اند قدیمی و مستقل که **از تیر ۱۴۰۵ دست نخورده** و هنوز توسط
GitHub Actions روی GitHub Pages منتشر می‌شود. محصول واقعی `website/` است.
هر تازه‌واردی این پوشه را پیدا می‌کند و منطقاً فکر می‌کند زنده است.

*پیشنهاد:* یا حذفش کن، یا یک `README` صریح داخلش بگذار که بگوید متروک است.

### ۶. تنها ورک‌فلوی CI، تست‌ها را اجرا نمی‌کرد
تا قبل از این مستندسازی، `.github/workflows/` فقط یک ورک‌فلوی انتشار
GitHub Pages داشت. حالا `tests.yml` اضافه شده که در هر push تست‌ها و
`docs/generate.py --check` را اجرا می‌کند.

### ۷. مسیریابی دستی API
هر مسیر جدید باید صریحاً به متد `do_*` اضافه شود، وگرنه بی‌صدا ۴۰۴ می‌دهد.
مهاجرت به FastAPI این کلاس از باگ را کامل حذف می‌کند و — چون منطقی داخل
`server.py` نیست — کار مکانیکی است.

## ✅ چیزهایی که بررسی شد و مشکل نداشت

برای اینکه کسی دوباره نگرانشان نشود:

- **رازها در گیت نیستند.** `.gitignore` درست کار می‌کند: `.env`، فایل‌های
  دیتابیس، `private_media/` (رسیدهای مشتریان) و `__pycache__` هیچ‌وقت کامیت
  نشده‌اند. تنها چیزی که در تاریخچه هست `.env.example` است.
- **هویت مشتری بین دو کانال درست ادغام می‌شود** — چهار تست مخصوص دارد.
- **همزمانی رزرو امن است** — ظرفیت و درج در یک تراکنش، و تغییر وضعیت‌ها
  با `set_status_if*`.

## 💡 قابلیت‌هایی که عمداً ساخته نشده‌اند

این‌ها «باقی‌مانده» نیستند، **تصمیم محصول‌اند** — در `01-product` هم آمده:
درگاه پرداخت آنلاین، پیامک، انتخاب صندلی روی نقشه‌ی سالن، کد تخفیف،
چندشعبه‌ای بودن، و اپلیکیشن موبایل.

اگر روزی یکی از این‌ها لازم شد، بزرگ‌ترینشان (درگاه پرداخت) کمترین ضربه را
به معماری می‌زند: یک وضعیت پرداخت جدید و یک سرویس، بدون دست زدن به ماشین
وضعیت رزرو — چون آن ماشین از قبل مفهوم «پرداخت انجام شد ولی هنوز تأیید
نشده» را دارد.
