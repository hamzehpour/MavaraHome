# ۰۶ — ربات تلگرام

ربات با **aiogram 3** نوشته شده. ~۱۷۵ هندلر در ۱۳ روتر. کل منطق تجاری‌اش در
`services/` است — همان کدی که API هم صدا می‌زند. هندلرها فقط دکمه و متن‌اند.

## پروسه و چرخه‌ی عمر

`bot/bot.py` (~۷۰ خط) نقطه‌ی شروع است و این کارها را می‌کند:

1. `init_db()` را صدا می‌زند — مایگریشن دیتابیس در استارت اجرا می‌شود.
   **از v19 پروسه‌ی API هم همین کار را می‌کند**، پس هرکدام زودتر بالا بیاید
   مایگریت می‌کند و دیگری no-op می‌شود. قبلاً فقط ربات مایگریت می‌کرد و
   اگر بالا نمی‌آمد، سایت روی اسکیمای قدیمی ۵۰۰ می‌داد.
2. ۱۳ روتر را با ترتیب ثابت ثبت می‌کند.
3. `delete_webhook(drop_pending_updates=True)` — پس پیام‌های صف‌شده‌ی زمان
   خاموشی پردازش نمی‌شوند.
4. سه حلقه‌ی پس‌زمینه راه می‌اندازد: انقضای رزروها، بکاپ دیتابیس، و تحویل
   صف `bot_outbox`.

اگر `BOT_TOKEN` نباشد، `bot.py` راه نمی‌افتد — ولی پروسه‌ی API بدون آن هم
کار می‌کند (عمدی است، چون هر دو یک `config/settings.py` را وارد می‌کنند).

## روترها

ترتیب ثبت در `bot.py`:

```
common → booking → payment → admin_reservations → admin_events → admin_panel
→ staff_manual_booking → support → bank_cards → overflow_requests
→ owner_management → channel_setup → reopening_interest
```

| روتر | خطوط | چه می‌کند |
|---|---|---|
| `common` | ۱۶۸ | `/start`، منوی اصلی، «رزروهای من»، ارسال مجدد رسید بعد از «نیازمند اصلاح» |
| `booking` | ۴۷۷ | جریان کامل رزرو: رویداد ← تاریخ ← سانس ← تعداد ← تأیید |
| `payment` | ۵۴ | دریافت عکس رسید از مشتری |
| `admin_reservations` | ۴۱۵ | صف بررسی رسیدها؛ تأیید / رد / نیازمند اصلاح |
| `admin_events` | ۶۹۳ | ساخت و ویرایش رویداد و سانس، ظرفیت، حذف |
| `admin_panel` | ۵۴۷ | منوی `/admin`: آمار، تنظیمات، مدیریت کارکنان، خروجی اکسل |
| `staff_manual_booking` | ۲۴۰ | ثبت رزرو به‌نیابت از مشتری + اسکن بلیت |
| `support` | ۶۹ | پیام پشتیبانی از مشتری |
| `bank_cards` | ۱۱۵ | افزودن/فعال‌سازی/حذف کارت بانکی |
| `overflow_requests` | ۹۶ | درخواست ظرفیت اضافه برای سانس پر |
| `owner_management` | ۱۰۹ | افزودن/حذف مالک با گذرواژه‌ی جدا و حذف تأخیری |
| `channel_setup` | ۱۵۷ | تنظیم کانال «برد فروش» زنده |
| `reopening_interest` | ۱۹۸ | «🔔 منتظر اجرای بعدی» |

> **ترتیب مهم است.** aiogram اولین هندلر منطبق را اجرا می‌کند. اگر هندلر
> جدیدی گذاشتی که پیام‌های عمومی را می‌گیرد، جای ثبتش را با دقت انتخاب کن.

## ماشین‌های حالت (FSM)

هر جریان چندمرحله‌ای یک `StatesGroup` در `bot/states/` دارد — مثلاً
`booking_states.py`، `admin_states.py`، `owner_states.py`. حالت‌ها فقط
نشانگرند؛ داده‌ی موقت در `state.update_data()` نگه داشته می‌شود و در پایان
جریان به یک تابع سرویس تحویل می‌شود.

**قاعده:** هیچ حالتی نباید داده‌ی ماندگار نگه دارد. اگر کاربر وسط کار برود،
تنها چیزی که از دست می‌رود یک فرم نیمه‌تمام است، نه یک رزرو.

## دسترسی‌ها

`services/permissions.py` **تنها منبع حقیقت** است. هندلرها هرگز نباید رشته‌ی
نقش را مستقیم مقایسه کنند؛ باید `has_permission()` را صدا بزنند.

**۱۴ دسترسی مجزا:**
`approve_payments` · `manual_booking` · `view_capacity` · `verify_tickets` ·
`request_overflow_decision` · `manage_events` · `manage_channel` ·
`manage_bank_cards` · `view_stats` · `export_data` · `manage_settings` ·
`broadcast` · `manage_staff` · `manage_ownership`

**نقش‌ها و گروه‌ها:**

| نقش/گروه | دسترسی‌ها |
|---|---|
| `owner` | **همه** |
| `admin` | همه به‌جز `manage_ownership` |
| `operator` (پشتیبانی) | تأیید پرداخت، رزرو دستی، مشاهده‌ی ظرفیت، بررسی بلیت |
| `finance` (مالی) | کارت‌های بانکی، آمار، خروجی داده |
| `sales` (فروش) | مثل operator + دریافت درخواست ظرفیت اضافه |
| `content` (محتوا) | مدیریت رویدادها، مدیریت کانال |

یک نفر می‌تواند **چند گروه** داشته باشد؛ دسترسی مؤثرش **اجتماع** آن‌هاست.

`owner` و `admin` عمداً در جدول گروه‌ها نیستند و در خود `has_permission()`
به‌صورت «همه‌چیز» / «همه‌چیز منهای مالکیت» حل می‌شوند — تا اضافه کردن یک
دسترسی جدید، نیاز به یادآوری برای به‌روزرسانی آن دو نداشته باشد.

**ایمنی انتقال مالکیت:** افزودن مالک جدید گذرواژه‌ی جداگانه می‌خواهد، و حذف
مالک **تأخیری** است (`admins.pending_removal_at`) — تا یک نشست لو رفته
نتواند بی‌سروصدا مالک واقعی را بیرون کند.

## متن‌ها

همه‌ی متن فارسی ربات در `bot/texts/fa.py` (~۵۲۷ خط) است. متن را داخل هندلر
هاردکد نکن.

قالب‌های پیامی که ادمین باید بتواند عوض کند (دستور پرداخت، تأیید بلیت، رد
رزرو و…) در جدول `settings` هستند، نه در `fa.py` — از پنل یا از منوی
تنظیمات خود ربات قابل ویرایش‌اند.

## ارسال ایمن پیام

`utils/safe_send.py` هر ارسال را می‌پوشاند: اگر Markdownِ نوشته‌شده توسط
ادمین خراب باشد (که پیش می‌آید، چون قالب‌ها ویرایش‌پذیرند)، تلگرام خطای
parse می‌دهد — و این تابع همان پیام را به‌صورت متن ساده دوباره می‌فرستد
به‌جای اینکه ارسال شکست بخورد. یک تست مخصوص از این رفتار محافظت می‌کند.

## حلقه‌های پس‌زمینه

| حلقه | فاصله | کار |
|---|---|---|
| انقضای رزرو | ۱۲۰ ثانیه | رزروهای `pending_payment` که مهلتشان گذشته → `expired` و آزادسازی صندلی |
| صندوق خروجی | چند ثانیه | تحویل ردیف‌های `bot_outbox` که پروسه‌ی API نوشته |
| بکاپ | دوره‌ای | کپی دیتابیس در `bot/backups/` |

## برد فروش کانال

اگر ادمین یک کانال تعیین کند، ربات به‌ازای هر رویداد+روز **یک پیام** نگه
می‌دارد و با هر رزرو **همان پیام را ویرایش می‌کند** (نه پیام تازه). نگاشت
پیام‌ها در `channel_boards` است. اگر متن از حد تلگرام بیشتر شود، به چند
بخش شکسته می‌شود.

هر وضعیت رزرو یک آیکون دارد (`_STATUS_ICON` در `services/channel_service.py`).
**اگر وضعیت جدیدی اضافه کردی، آیکون و شمارش‌های خلاصه را هم به‌روز کن** —
وگرنه ردیف با آیکون پیش‌فرض «•» ظاهر می‌شود و در هیچ شمارشی حساب نمی‌شود.

## چیزی که تست نمی‌شود

`test_bot.py` **هیچ هندلر تلگرامی را اجرا نمی‌کند** — نه مسیریابی callback،
نه رندر کیبورد، نه پروتکل تلگرام. داکسترینگ خودش این را صریح گفته: این‌ها
اجرای واقعی ربات می‌خواهند.

آنچه تست می‌شود، لایه‌ی زیرین است: همان توابع `services/` که هندلرها صدا
می‌زنند. پس منطق تجاری پوشش دارد، ولی «آیا این دکمه به تابع درست وصل است؟»
فقط با تست دستی معلوم می‌شود.

## افزودن یک قابلیت جدید به ربات

1. اگر منطق تجاری دارد: تابعش را در `services/` بنویس (و تستش را در
   `test_bot.py`).
2. متن‌ها را به `texts/fa.py` اضافه کن.
3. اگر چندمرحله‌ای است: یک `StatesGroup` در `states/` بساز.
4. کیبورد را در `keyboards/` بساز.
5. هندلر را در روتر مناسب بنویس — یا اگر حوزه‌ی جدیدی است، روتر تازه بساز و
   **در `bot.py` ثبتش کن** (فراموشی این مرحله = هندلری که هرگز اجرا نمی‌شود).
6. اگر دسترسی‌محور است، در `permissions.py` یک ثابت جدید تعریف کن و با
   `has_permission()` چکش کن.
